# Database

The migrations are the authority for the schema. They live in
`../backend/internal/store/postgres/migrations` rather than here, because they
are embedded into the Go binary with `go:embed`: the image that serves the API
is the image that migrates the database, so the two can never be out of step.

```
0001_core.up.sql / .down.sql                 organisation and master data
0002_planning.up.sql / .down.sql             seasons, versions, assumptions, daily facts
0003_execution.up.sql / .down.sql            orders, confirmations, inventory documents
0004_quality_downtime.up.sql / .down.sql     specs, samples, holds, downtime, maintenance
0005_security_governance.up.sql / .down.sql  identity, approvals, audit, outbox, jobs
0006_negative_stock.up.sql / .down.sql       relax the stock_balances hold check
```

## Running them

**With the migration tool** — the normal way. It records what it applied in
`schema_migrations` and runs each migration in its own transaction, so an
interrupted upgrade leaves the database on a known version.

```bash
cd ../backend
export STORE=postgres DATABASE_URL='postgres://user:pass@host:5432/sugarplan?sslmode=require'
export APP_ENV=development AUTH_MODE=dev AUTH_DEV_SECRET=local-development-secret

go run ./cmd/migrate up          # apply everything pending
go run ./cmd/migrate status      # what is applied, what is pending
go run ./cmd/migrate down -steps 1
go run ./cmd/migrate seed        # the reference scenario; refused in production
```

**With psql** — for a DBA who wants to read them before they run, or for a site
whose change process requires SQL files.

```bash
cd ../backend/internal/store/postgres/migrations
for f in 0001_core 0002_planning 0003_execution 0004_quality_downtime 0005_security_governance; do
  psql -v ON_ERROR_STOP=1 -f "$f.up.sql" "$DATABASE_URL"
done
```

Applying them by hand does not populate `schema_migrations`; insert the rows, or
let the tool take over from the next migration onwards.

## Conventions

- snake_case names, UUID primary keys generated by the application
- quantities `numeric(18,3)`, rates `numeric(12,3)`, factors `numeric(18,6)` —
  never floating point
- every mutable table carries `created_at`, `created_by`, `updated_at`,
  `updated_by` and `row_version`
- master data is deactivated, never deleted
- `audit_events` is append-only, enforced by rules as well as by grants

See [../docs/05-data-model.md](../docs/05-data-model.md) for the ERD, the data
dictionary and the reasoning.

## Least-privilege grants

```sql
GRANT USAGE ON SCHEMA public TO sugarplan_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO sugarplan_app;
REVOKE UPDATE, DELETE ON audit_events FROM sugarplan_app;
```

The migration role and the application role should be different: the application
has no business creating tables.
